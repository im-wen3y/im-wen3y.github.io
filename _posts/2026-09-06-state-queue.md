## 왜 이 글을 쓰게 되었나

`+2` 버튼을 만드는 PR을 리뷰하다가, 화면에 몇이 찍힐지 확신이 안 서서 손이 멈췄다.
setState가 비동기라는 건 알고 있었는데, 그게 이 코드에서 정확히 무슨 뜻인지는 설명하지 못했다.

## 리뷰한 PR

요구사항: **초기 수량 1, 버튼을 한 번 누르면 2개 늘어난다.**

**Quantity.jsx**
{: .filename}

```diff
 function handleClick() {
   setQuantity(quantity + 1);
+  setQuantity(quantity + 1);
 }
```

`+1` 버튼을 `+2`로 바꾸면서, 호출을 한 줄 더 넣은 변경이다.

## 처음 든 생각

setState가 비동기라는 건 알고 있었다. 그래서 이렇게 적었다.

> useState는 비동기적으로 값이 업데이트 되지 않아?
> handleClick 시에 setQuantity를 두 번 호출할 때, 두 번째 quantity의 예측이 안 될 것 같다.

"예측이 안 된다"는 게 사실 정직한 상태였다. 두 번째 호출이 1을 보는지 2를 보는지 확신이 없었다.

정리하고 나니 이렇게 되는 거였다.

**Quantity.jsx — 실제로 실행되는 것**
{: .filename}

```js
setQuantity(quantity + 1);  // 1 + 1
setQuantity(quantity + 1);  // 여기도 1 + 1
```

두 호출 모두 **이번 렌더링에 고정된 `quantity` 값 1**을 읽는다. 이벤트 핸들러가 도는 동안 `quantity`는 변하지 않는다.
그래서 둘 다 "2로 바꿔줘"가 되고, 화면에는 3이 아니라 **2**가 찍힌다.

요구사항은 2 증가인데 실제로는 1 증가. 승인하지 않고 수정 요청.

## 수정 제안

**Quantity.jsx — 수정 제안**
{: .filename}

```js
setQuantity(q => q + 1);
setQuantity(q => q + 1);
```

여기서 한 번 더 헷갈렸다. **`q`가 바깥 `quantity`와 같은 값인가?** 하고.

아니었다. `q`는 그냥 화살표 함수의 매개변수 이름이고(JS 문법), 값은 React가 넣어준다.
넣어주는 값은 렌더링 시점의 스냅샷이 아니라, **큐를 처리하면서 직전 항목까지 계산된 결과**다.

| | 언제 정해지나 | 값의 출처 |
|---|---|---|
| `quantity` | 클릭한 순간 | 이번 렌더링에 고정된 스냅샷 |
| `q` | 렌더링 직전, 큐 처리 중 | 큐에서 직전 항목까지의 결과 |

## 섞으면 순서가 결과를 바꾼다

이해했는지 확인하려고 순서를 바꿔봤다.

**순서를 바꿔본 것**
{: .filename}

```js
// n === 0
setNumber(n => n + 1);   // 0 → 1
setNumber(n + 1);        // "1로 교체" — 앞의 결과를 덮어씀
setNumber(n => n + 1);   // 1 → 2
```

결과는 3이 아니라 **2**.
값 전달은 호출하는 순간 이미 숫자로 굳어져서, 큐를 처리할 때 그때까지 굴러온 값을 덮어쓴다.
갱신 함수는 함수인 채로 쌓였다가 직전 결과를 받아 이어서 계산한다.

## 배운 점

- setState가 "비동기"라는 말로 뭉뚱그려 알고 있었는데, 실제로는 **스냅샷**과 **큐**라는 두 가지를 나눠서 봐야 했다.
- 리뷰어 입장에서는 "여기 버그다"보다 **재현 조건과 영향**을 같이 쓰는 게 중요하다는 피드백을 받았다. (버튼 1회 클릭 시 항상 1만 증가 → 주문 수량이 사용자 의도와 어긋남)
- 같은 핸들러에서 값 전달과 갱신 함수를 섞으면 읽는 사람이 큐를 손으로 추적해야 한다. 버그는 아니지만 리뷰에서 짚을 만한 지점.

## AI를 어떻게 썼나

AI에게 PR 작성자 겸 튜터 역할을 맡기고, 답을 먼저 알려주지 않게 해두었다.
예측과 리뷰는 내가 쓰고, 틀린 지점에서만 큐를 한 줄씩 따라가는 힌트를 받았다.
